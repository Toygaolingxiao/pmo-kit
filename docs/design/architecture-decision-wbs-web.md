# WBS Web 复刻架构决策（v0.1）

## 结论先行

当前 `wbs-excel-source-analysis.md` 是一份很有价值的**需求与行为逆向分析**，但不是足以实现
像素级 1:1 的原始规格。它明确指出缺少原始 Excel 的：

- 单元格样式、颜色、边框、列宽、行高、冻结窗格；
- 公式与计算链；
- VBA / 宏；
- 原始截图和实际操作录屏。

因此本项目采用两条验收线：

1. **行为 1:1**：以分析文件中的字段、流程、计算规则、导入导出和边界条件为准，逐项实现并测试。
2. **视觉 1:1**：必须取得原始 `.xlsx`、关键页面截图及可用的宏/公式信息后，逐页校准；在此之前只承诺
   Excel 风格和明确的视觉语义，不承诺像素级复刻。

## 技术选型

### 保留的现有核心

- **Node.js 20 + TypeScript**：继续作为 JSON 校验、计算、HTML/CSV/Mermaid/周报渲染的共享核心。
- 现有 `src/render.ts` 不改造成 UI；它保持无状态、可脚本调用、适合客户交付和 CI。
- `project-plan.json` 继续作为可读、可 diff、可版本管理的交换格式。

### 新增的 Web 编辑层

| 层 | 选择 | 原因 |
| --- | --- | --- |
| 构建 | Vite | 本地工具启动快、部署简单，不引入服务端框架负担 |
| UI | React + TypeScript | 表格编辑、键盘交互、组件拆分和生态最适合本项目 |
| 状态 | Zustand | 编辑器状态直观，适合撤销/重做和脏状态管理 |
| 表格模型 | TanStack Table | 无样式绑定，可保留 Excel 风格布局；不被通用甘特视觉限制 |
| 虚拟化 | TanStack Virtual | 同时覆盖任务行和日期列，目标支持 500 行 × 365 天 |
| 日期 | `date-fns` | 纯函数、可测试，避免时区和 Excel serial date 混入领域模型 |
| 甘特层 | 自研 DOM/SVG overlay | 原表是“冻结任务列 + 日期网格 + 稲妻线”，通用甘特图库很难 1:1 |
| 校验 | Zod（运行时）+ TypeScript（编译时） | JSON、粘贴、导入和 URL 数据都必须运行时校验 |
| Excel | ExcelJS（服务/Node 导出优先） | 需要 sheet、样式、日期和合并单元格的可控处理 |

不首选 AG Grid、dhtmlxGantt 或商业甘特组件：它们可以快速得到普通任务表，但会限制
冻结列、周会行、休日行、稲妻线和原 Excel 布局的精确控制，并可能带来许可或 bundle 负担。

## 运行形态

### 阶段 A：本地优先（首选起点）

- Vite + React 的编辑器在浏览器中运行；
- 通过 `project-plan.json` 导入和导出；
- IndexedDB 保存本地草稿和撤销快照；
- 每次“更新”生成确定性的计算结果，再调用共享领域逻辑渲染；
- 不引入账号、数据库、网络同步。

这样符合 pmo-kit 现有的“本地、可版本管理、可交付”定位，也能先验证最难的表格体验。

### 阶段 B：可选服务端

只有在确认需要多人协作、权限隔离、审计日志或集中模板库后，才增加：

- Node.js + Fastify API；
- SQLite（单机/小团队）或 PostgreSQL（多人部署）；
- 项目、任务、日历、模板、变更履历的事务边界；
- 服务端权限校验和审计。

不在第一阶段引入后端，避免还没有验证交互模型就锁定数据库和权限设计。

## 功能边界与实施顺序

### F0：基线与领域模型

- 建立 `ProjectPlan`、`WbsTask`、`CalendarHoliday`、`WeeklyMeeting`、`ChangeLog` 类型；
- 兼容现有 `wbs[].start/end/pct` 字段；
- 新字段采用可选字段，旧示例必须继续渲染；
- 统一 ISO 日期和明确的项目时区；
- 建立 `planStart/planEnd/dataDate`、休日、周末和日期轴的纯函数；
- 为所有计算函数写单元测试。

### F1：可用的 WBS 编辑器

- 项目头部：名称、阶段、开始日、创建/更新信息；
- 左侧冻结任务列：项番、大/中/小项目、说明、负责人、成果物、remote；
- 双击编辑、Enter、Tab、Esc、Ctrl+Z、Ctrl+Y；
- 新增、删除、排序、缩进、升级、折叠/展开；
- 任务详情抽屉；
- 计划/实绩/进度字段与严格校验。

### F2：日期轴与甘特图

- 月份、日期、星期三层表头；
- 休日行、周会 `●` 行；
- 30/60/90/180 天和自动适配范围；
- 左侧冻结、右侧横向滚动、表头吸顶；
- 计划条、实绩条、进度条、里程碑、今天线；
- 支持任务条拖拽修改起止日和平移。

### F3：更新、稲妻线和履历

- 编辑后局部预览，明确的“更新/保存”动作；
- 计划进度率、实际进度点和提前/延迟规则；
- SVG 稲妻线 overlay；
- 自动/手动变更履历；
- 基于快照的撤销、重做和脏状态提示。

### F4：模板和 Excel 兼容

- 把原 WBS 样例整理为可筛选的标准任务模板；
- 追加、覆盖、插入到选中任务下三种导入方式；
- Excel serial date、合并单元格、空白行、跨行继承和多行文本；
- 导入预览、错误行定位和确认后提交；
- 导出 WBS、说明、变更履历、WBS 样例四类 sheet；
- 导出后再次导入的 round-trip 测试。

### F5：产品化（不默认承诺）

- 多项目索引、账号、权限、服务端审计、通知和集中模板库；
- 这些功能必须在本地编辑体验稳定后单独立项。

## 不可省略的实现约束

1. **不能把每天渲染成大量 React 组件。** 甘特条用绝对定位，稲妻线用单个 SVG overlay，
   日期和任务行采用双向虚拟化。
2. **不能把“更新”当成纯按钮装饰。** 更新必须执行日期轴、进度、偏差、父任务汇总和履历计算，
   并产生可测试的结果。
3. **不能先做普通任务列表再补甘特。** 冻结列、横向日期轴、滚动同步和编辑状态必须从第一版
   作为同一个网格模型设计。
4. **不能直接信任导入内容。** JSON、Excel、粘贴文本都要经过运行时校验，并防止公式注入和 HTML/XSS。
5. **不擅自推断 Excel 未知公式。** 对缺失信息先建立“可配置计算策略”，拿到原文件后用样例逐项校准。

## 1:1 验收标准

### 行为验收

- 500 行任务、365 天日期轴仍能滚动和编辑；
- 修改项目开始日会同步移动日期轴；
- 周末/额外休日、周会 `●`、今天线与任务条位置正确；
- 计划/实绩/进度字段和日期异常给出明确错误；
- 进度提前显示在右侧，延迟显示在左侧，未开始任务不误报延迟；
- 样例导入不破坏现有任务，覆盖操作有确认；
- 导出再导入后，任务层级、日期、文本、周会和休日无数据丢失；
- 每个会改变计划的操作都能产生履历。

### 视觉验收

拿到原始 Excel 后，针对 WBS 主表、说明、变更履历、样例四个页面建立截图对照：

- 列顺序、表头层级、颜色、边框、行高、冻结区域；
- 计划条、实绩条、休日、今天线、稲妻线和里程碑；
- 关键键盘操作和拖拽后的视觉反馈。

没有原始 `.xlsx` 或截图时，只能做行为验收，不能诚实地宣称像素级 1:1。

## 当前建议

先不要安装一堆 UI 或甘特依赖，也不要马上开发后端。下一步应是：

1. 获取原始 `.xlsx`、至少 4 页截图和是否存在宏/VBA 的信息；
2. 按 F0 建立共享领域类型、日期/进度计算和测试；
3. 用一个真实样例完成 F1 的冻结网格原型；
4. 以性能和键盘编辑体验通过为门槛，再进入 F2；
5. 每完成一个阶段，把对应验收项写成自动化测试和一份可打开的示例输出。
