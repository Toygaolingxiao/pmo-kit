> 排定投资顺序、定义数据边界和验收质量的共同基线。
>

## 1. 结论先行

pmo-kit 不应被设计成“更多功能的 Excel”，也不应成为 Jira、ERP 或 BI 的低配复制品。
它的最佳定位是：

> **面向项目负责人、PMO 和咨询顾问的本地优先项目控制塔：把承诺、计划、执行证据、
> 风险、决策、变更和管理层沟通串成一条可追溯链路。**

工具的核心价值不是“画出甘特图”，而是让管理者在固定节奏下回答五个问题：

1. 我们承诺交付什么，验收标准是什么？
2. 当前计划是否仍然可信，关键路径在哪里？
3. 哪些风险、问题或决定正在威胁承诺？
4. 本周需要谁在什么时候做出什么决定？
5. 面向客户和管理层，哪些事实、证据和行动必须被透明地呈现？

因此产品必须围绕一个闭环建设：

```text
承诺与目标
  -> 范围/WBS/里程碑
  -> 计划/资源/执行证据
  -> RAID/决定/变更
  -> 周期性状态与治理会议
  -> 预测/行动/重新承诺
  -> 版本化交付与复盘
```

## 2. 设计原则

### 2.1 先保证管理闭环，再增加页面

每个模块必须至少连接一个上游对象和一个下游决策：

| 模块 | 上游 | 下游 |
| --- | --- | --- |
| WBS | 目标、范围、交付物 | 里程碑、状态、证据 |
| RAID | WBS、假设、依赖 | 行动、决定、升级 |
| 变更 | 基线、需求、风险 | 影响评估、审批、重排 |
| 状态报告 | 计划、RAID、指标 | 治理会议、客户沟通 |
| 复盘 | 版本、事件、结果 | 模板、估算和风险规则改进 |

孤立的“备注页”“漂亮仪表盘”不进入第一优先级。

### 2.2 交付物优先，而非任务数量优先

任务不是管理成果。每个可管理的工作包都应尽量具备：

- 明确交付物；
- 可验证的验收标准；
- 单一 accountable owner；
- 计划和实际日期；
- 依赖和风险；
- 完成证据或链接。

### 2.3 事实、判断、承诺分离

系统要区分：

- **事实**：实际发生了什么，有何证据；
- **判断**：当前预测、风险等级、管理意见；
- **承诺**：谁在何时完成什么；
- **决定**：谁基于哪些选项批准了什么。

这样才能避免把“状态颜色”误当成事实，也避免周报变成手工润色的叙述。

### 2.4 默认本地优先，协作能力后置

第一阶段继续支持：

- JSON 可读、可 diff、可纳入 Git；
- 浏览器本地编辑；
- Excel/CSV/HTML/Mermaid/Markdown 导出；
- 离线可用；
- 不强制账号和服务器。

多人协作、权限、审批和通知只有在数据模型与单机体验稳定后引入。

### 2.5 可解释、可回溯、可恢复

任何自动计算都必须能回答：

- 输入是什么；
- 规则是什么；
- 结果是什么；
- 哪次更新产生了结果；
- 如何撤销或重算。

禁止不可解释的“AI 自动改计划”作为默认行为。

## 3. 目标用户与典型场景

### 3.1 目标用户

| 用户 | 主要任务 | 成功标准 |
| --- | --- | --- |
| 项目经理 | 建计划、推进执行、预测交付 | 10 分钟内形成可信周报 |
| PMO | 跨项目治理、风险升级、会议准备 | 发现问题早于项目红灯 |
| 咨询顾问 | 快速搭建项目控制体系、交付客户 | 模板可复用、输出可交付 |
| 工作流负责人 | 更新任务、提交证据、响应行动项 | 不需要学习复杂系统 |
| Sponsor/客户 | 查看状态、决策和承诺 | 只看到相关、可信和可行动的信息 |

### 3.2 三个优先场景

1. **项目启动**：从标准模板建立章程、范围、WBS、治理节奏、RAID 初始库。
2. **每周治理**：刷新进度、风险、决定、行动，自动生成状态包和会议议程。
3. **变更与复盘**：记录基线变化、影响、审批和结果，沉淀为下一项目模板。

## 4. 能力地图

能力分为六层。每层都有明确边界，避免把所有需求塞进 WBS。

### L1：项目基础与治理（Project Foundation）

- 项目章程：目标、范围边界、成功指标、约束、Sponsor；
- 项目阶段与 Stage-Gate；
- 组织、角色、RACI；
- 治理节奏：周会、SteerCo、工作组；
- 会议、议程、材料和行动项；
- 项目基线与版本。

### L2：交付计划与执行（Delivery Control）

- WBS、交付物、验收标准；
- 里程碑、依赖、关键路径；
- 甘特、日历、工作日、休日、实绩；
- 资源/工数计划；
- 进度预测、稲妻线、偏差分析；
- 任务证据与完成定义。

### L3：风险、问题和决定（Control & Decisions）

- Risk、Assumption、Issue、Dependency（RAID）；
- 决策日志与选项比较；
- 行动项与升级规则；
- 变更请求、影响分析、审批；
- RAID 与 WBS、里程碑、会议的双向关联。

### L4：质量、范围和结果（Assurance & Outcomes）

- 需求/范围清单；
- 质量计划、检查点、缺陷和审计证据；
- 测试/验收追踪；
- 交付物审查；
- 业务结果、收益、KPI 和 OKR 关联；
- 上线准备和运营交接。

### L5：组合与管理层视图（Portfolio Intelligence）

- 多项目索引；
- 统一状态口径；
- 项目健康评分；
- 资源冲突与跨项目依赖；
- 投资、收益、风险暴露；
- 管理层决策队列。

### L6：资产、模板与学习（PMO Asset System）

- 行业/项目类型模板；
- 标准 WBS、RAID、会议和周报模板；
- 字段字典、状态字典、风险评分矩阵；
- 变更履历和版本比较；
- 复盘知识库；
- 可导出客户交付包。

## 5. 模块设计

### 5.1 Project Hub：项目总览

项目总览不是仪表盘拼贴，而是一个“下一步行动页”：

- 项目目标、范围和当前阶段；
- 当前基线与数据日期；
- 三个最重要的交付/里程碑；
- Top risks/issues/decisions；
- 本周到期行动；
- 绿/黄/红状态及其证据；
- 最近变更和下一治理会议。

每个颜色必须可下钻到事实；不允许手工选择红黄绿却没有理由。

### 5.2 Charter & Scope：章程与范围

- 目标、非目标、成功指标；
- 交付物清单；
- 范围内/范围外；
- 假设与约束；
- Sponsor、PM、核心团队；
- Stage-Gate 与退出标准；
- 版本化基线。

范围对象必须能引用到 WBS、需求、变更和验收证据。

### 5.3 WBS & Schedule：交付计划核心

沿用现有 Excel 逆向成果，完整支持：

- 大/中/小项目与作業詳細层级；
- 计划/实际/预测三套时间语义；
- 工数、负责人、成果物、验收标准；
- 依赖、里程碑、关键路径；
- 休日、周会、今天线；
- 冻结列、日期虚拟化、拖拽和键盘编辑；
- 稲妻线、偏差和父任务汇总；
- WBS 样例导入、Excel round-trip；
- 任务完成证据和 checklist 引用。

WBS 的“完成”必须由交付物和验收标准定义，而不只是 `pct = 100`。

### 5.4 RAID：风险与问题控制

统一对象字段：

```text
id / type / title / description / owner / status
probability / impact / exposure / response
dueDate / escalationLevel / linkedWbs / linkedMilestones
createdAt / updatedAt / closedAt / evidence
```

要求：

- Risk 与 Issue 不混淆；
- Assumption 到期后可转为 Risk；
- Dependency 有供方、受方和承诺日期；
- 每个高暴露项必须有 owner、response 和 due date；
- 过期项自动进入周报和决策队列；
- 关闭必须保留结果和证据。

推荐风险评分：`probability × impact`，评分矩阵可配置，但历史评分不可被静默重写。

### 5.5 Decision Log：决定管理

每条决定至少记录：

- 决策问题；
- 背景和截止日期；
- 选项及评估维度；
- 推荐方案；
- 决策人；
- 决策日期；
- 影响到的范围、WBS、预算、风险和里程碑；
- 决定后的行动；
- 附件或会议证据。

系统应突出“待决定年龄”和“逾期决定”，因为决策延迟通常先于进度红灯。

### 5.6 Change Control：变更控制

变更状态：

```text
draft -> impact_assessment -> submitted -> approved/rejected -> implemented -> verified
```

影响分析至少覆盖：

- 范围；
- 日期和关键路径；
- 工数/成本；
- 资源；
- 风险；
- 质量；
- 合同/客户承诺。

批准后才能更新基线；更新前后必须可比较，并自动生成变更履历。

### 5.7 Resource & Effort：资源与工数

第一阶段只做项目级轻量能力：

- 角色和可用性；
- 任务计划工数/实际工数；
- 人日按周/月汇总；
- 过载和空闲提示；
- 外部依赖和供应商责任。

不在早期做薪资、复杂排班和 ERP 级成本核算。只有当工数口径稳定后，才扩展预算/成本。

### 5.8 Quality & Acceptance：质量与验收

- 质量门禁与检查表；
- 交付物审查；
- 缺陷/问题；
- 测试计划、执行、证据；
- 客户验收状态；
- 未关闭缺陷对里程碑的影响；
- Definition of Ready / Done。

质量对象应与成果物和里程碑关联，不另造孤立的“质量页面”。

### 5.9 Communication & Status：沟通与周报

自动生成但允许人工审阅：

- 一页式 Executive status；
- 本周完成/下周计划；
- 里程碑预测；
- RAID 变化；
- 决策请求；
- 需要 Sponsor 升级的事项；
- 变更摘要；
- 证据链接。

状态报告必须标出“数据日期”和“手工叙述”，避免过期数据伪装成当前事实。

### 5.10 Benefits & KPI：结果与收益

项目不应以“任务全部完成”作为唯一成功：

- 结果指标；
- 基线、目标、当前值；
- 指标负责人；
- 测量频率；
- 收益实现日期；
- 预期/实现差异；
- 结果证据。

该模块在项目核心闭环稳定后建设，不应先做成泛化 BI。

### 5.11 Portfolio：组合视图

支持：

- 项目清单和阶段；
- 统一健康状态；
- 关键里程碑；
- 高暴露 RAID；
- 资源冲突；
- 跨项目依赖；
- 决策/审批队列。

组合层只消费项目层已定义的数据，不重新发明状态口径。

### 5.12 Templates & Playbooks：模板资产

模板类型：

- 项目章程；
- WBS；
- RAID；
- 周报；
- 会议议程；
- 质量门禁；
- 上线/交接；
- 复盘。

模板必须有版本、适用场景、维护者和示例项目，不能把模板散落在代码和个人文件夹中。

## 6. 统一数据底座

### 6.1 核心实体

```text
Portfolio
Project
ProjectVersion / Baseline
StageGate
Objective
Deliverable
WbsTask
Milestone
Dependency
Calendar
Resource / Role
RaidItem
Decision
Action
ChangeRequest
Requirement
QualityCheck / Defect / Evidence
Meeting / StatusReport
BenefitMetric
Template
AuditEvent
```

### 6.2 关系原则

- `Project` 是边界，不允许跨项目对象无引用地漂移；
- `WbsTask` 是交付执行的主链接点；
- `Deliverable` 是任务、质量、验收和结果的共同语言；
- `Baseline` 记录承诺，`Forecast` 记录当前判断，`Actual` 记录事实；
- `Decision` 和 `ChangeRequest` 是治理事件，不应被普通备注替代；
- 所有日期必须使用 ISO 日期，并显式包含项目时区；
- 所有可变对象有稳定 ID，不使用行号作为外键。

### 6.3 向后兼容策略

保留现有 `project-plan.json` 最小字段：

```text
meta / milestones / sprints / roles / raci / raid / org / wbs
```

新增能力采用可选命名空间：

```text
calendar / baselines / forecasts / decisions / actions
changes / requirements / quality / meetings / benefits / templates
```

旧文件必须仍能被渲染；升级工具负责显式迁移，禁止静默改写用户文件。

## 7. 产品架构

### 7.1 分层

```text
UI Shell
  -> Feature modules (WBS, RAID, Status, Portfolio...)
  -> Application commands / queries
  -> Domain services and pure calculations
  -> Project-plan document adapter
  -> JSON / XLSX / CSV / HTML / Markdown / Mermaid
```

现有 `src/render.ts` 保持无状态渲染核心，不把它改造成前端状态容器。

### 7.2 推荐技术路线

- TypeScript：共享领域类型和计算规则；
- React + Vite：本地 Web 编辑器；
- Zustand：编辑状态、撤销/重做、脏状态；
- TanStack Table/Virtual：高性能网格；
- DOM/SVG：甘特条、今天线、稲妻线；
- Zod：运行时导入校验；
- ExcelJS：Excel 读写和样式兼容；
- IndexedDB：本地草稿和快照；
- Vitest/Playwright：纯函数、导入导出和关键交互测试。

后端候选为 Fastify + SQLite/PostgreSQL，但只有协作、审计或集中模板成为真实需求时启用。

### 7.3 命令模型

重要写操作使用明确命令，而不是组件直接改对象：

```text
createTask
moveTask
setTaskActual
updateBaseline
createRaidItem
recordDecision
submitChange
approveChange
publishStatusReport
restoreSnapshot
```

命令产生领域事件和变更摘要，方便撤销、审计、同步和测试。

## 8. 路线图与放行门槛

### Phase 0：基线与逆向（当前）

交付：

- Excel 样式/公式/合并/冻结/验证/宏快照；

- 现有 JSON 的兼容测试；
- 产品蓝图和范围基线。

放行：样例可解析，关键规则有可重复测试，未知行为被标记而非猜测。

- 撤销/重做、版本快照。

放行：500 行 × 365 天可用；真实 Excel round-trip 无关键数据丢失。

放行：一次完整周会可在系统中完成，会议后能追踪到决定和行动。

交付：

- 章程/范围/Stage-Gate；
- 质量门禁、验收和缺陷；

- 上线与运营交接。

放行：项目从启动到验收的主线对象可追溯。

### Phase 4：组合与模板资产

交付：

- 多项目索引；
- 跨项目风险/依赖；
- 组合健康视图；
- 模板库和版本管理；
- 项目复制和初始化向导。

放行：同一套状态口径可覆盖多个项目而不依赖手工二次整理。

### Phase 5：可选协作平台

仅在有明确需求时建设：

- 账号和权限；
- 多人并发；
- 服务端审计；
- 通知；
- 集中存储和 API；
- 与 Git/文档/工时系统集成。

## 9. 管理口径与计算规则

### 9.1 计划、预测、实际三分法

- Planned：当前批准基线；
- Forecast：基于当前事实的预计结果；
- Actual：已发生并有记录的事实。

任何状态页同时展示三者，禁止用实际值覆盖基线。

### 9.2 健康状态

状态由规则产生、由 PMO 审阅：

- Green：承诺可达成，无需管理层介入；
- Amber：存在可控偏差，需要明确行动或决定；
- Red：承诺或阶段目标已受威胁，需要升级/重承诺。

状态理由必须引用指标、RAID、决定或变更。

### 9.3 预测指标

第一版只采用可解释指标：

- 里程碑预测偏差；
- 关键路径剩余浮动；
- 计划完成率 vs 实际完成率；
- 逾期行动数；
- 高暴露 RAID 数；
- 决策逾期天数；
- 变更请求待批金额/工数/天数。

不在早期引入没有数据基础的复杂预测模型。

## 10. 非功能标准

### 正确性

- 日期、时区、休日和工作日规则可测试；
- 导入失败指出行、列和原因；
- 导出再导入保持语义；
- 所有关键计算可解释。

### 性能

- 500 行 × 365 天仍可滚动和编辑；
- 初次打开典型项目 < 2 秒（本地生产构建目标）；
- 编辑反馈 < 100ms；
- 大型日期网格采用虚拟化。

### 安全与隐私

- 默认不上传项目数据；
- 导入内容防止公式注入、XSS 和路径穿越；
- 未来服务端采用最小权限、租户隔离和审计；
- 日志不记录客户机密和凭证。

### 可维护性

- 领域逻辑不依赖 React；
- 所有格式适配器可独立测试；
- schema 有版本；
- 破坏性迁移有迁移说明和回滚路径。

## 11. MBB 级治理机制

### 每周治理包

固定输出：

1. 本周状态和状态理由；
2. 关键里程碑预测；
3. Top 5 RAID；
4. 待决策事项；
5. 逾期行动；
6. 本周完成和下周承诺；
7. 变更和基线影响；
8. 需要 Sponsor/客户介入的事项。

### Stage-Gate 检查

每个阶段必须同时满足：

- 交付物完成；
- 验收证据齐全；
- RAID 有明确处置；
- 决策没有阻塞项；
- 下一阶段资源和计划已批准；
- 状态报告已发布。

### 复盘

复盘不只记录感想，至少捕获：

- 原计划与实际差异；
- 触发差异的早期信号；
- 哪个决定/假设影响最大；
- 哪条模板或规则需要修改；
- 下一项目如何提前检测。

## 12. 产品成功指标

### 使用指标

- 从空项目到首份可信计划的时间；
- 每周状态报告生成时间；
- WBS/Excel round-trip 成功率；
- 任务、RAID、决定的有效关联率；
- 过期行动项关闭率。

### 管理结果指标

- 风险从发现到响应的中位时间；
- 决策从提出到决定的中位时间；
- 里程碑预测准确度；
- 变更影响评估完整率；
- 阶段 Gate 一次通过率；
- 复盘行动在下一项目中的复用率。

不把页面访问量或图表数量作为主要成功标准。

## 13. 明确不做的事情

在没有新证据前，以下不进入核心范围：

- 复制完整 Jira/ERP/财务系统；
- 复杂自动排程黑盒；
- 默认实时多人协作；
- 强制云端账号；
- 用 AI 自动修改基线；
- 只展示没有证据的高级 BI；
- 为每个客户定制不可迁移的字段；
- 为了“看起来完整”而创建没有治理用途的模块。
